# 0012. 디자인의 원본을 어디에 둘까 — 컴포넌트 · 동기화 (제안)

- 상태: **승인** (2026-11-27 — 사용자: "코드가 원본 + 갤러리" 로 진행)
- 질문(사용자): 여러 페이지가 함께 쓰는 컴포넌트를 피그마처럼 한 곳에서 고치면 모든 페이지에 반영되게 할 수 있나? 개발 후에도 디자인과 소스 코드가 100% 동기화될 수 있나? 가능하면 피그마로, 작은 컴포넌트 단위로.

## 1. 지금 무엇이 문제인가 (사실)

| 항목 | 현재 |
| --- | --- |
| 게임 카드 마크업을 만드는 곳 | **9곳** — 생성기 `mg.py` · `pages3/5/6.py` · `pg_mobile.py` · `build.py` · 템플릿 2개 + 손으로 만든 `PG01` · `DS04`(각각 카드 16 · 13개 사본) |
| 헤더 | 3곳 |
| 공통인 것 | 토큰(tokens.css)과 공통 CSS(common.css)는 한 곳 — 그래서 3차 피드백의 테두리 · 툴팁은 한 번에 퍼졌다 |
| 캔버스 자체 컴포넌트 기능(`dc-import`) | 쓰지 않음 |

→ 사용자 우려가 맞다. **CSS 는 공유되지만 마크업(구조)은 복제돼 있어서**, 구조를 바꾸면 페이지마다 따로 고쳐야 하고 빠뜨리기 쉽다(PG03 툴팁 사고가 그 예).

## 2. "100% 동기화"의 조건

원본이 **두 개**(디자인 파일 + 코드)면 어떤 도구를 써도 100% 는 불가능하다 — 사람이든 AI 든 옮기는 단계에서 어긋난다. 100% 는 **원본이 하나이고 다른 쪽이 그것에서 자동으로 만들어질 때만** 성립한다.

## 3. 선택지 비교

| 기준 | A. 피그마가 원본 | B. 지금 캔버스를 컴포넌트화(`dc-import`) | C. **코드가 원본** + 컴포넌트 갤러리를 아티팩트로 게시 |
| --- | --- | --- | --- |
| 한 곳 고치면 모든 페이지 반영 | ○ (피그마 컴포넌트) | ○ (캔버스 안에서만) | ○ |
| 코드와 100% 동기화 | ✕ 원본 둘. Code Connect 로 연결만 가능 | ✕ 원본 둘. 캔버스 형식(React 런타임 · 식 없는 템플릿)을 Svelte 로 매번 옮김 | **◎ 갤러리가 코드를 빌드한 결과 그 자체** |
| Claude 가 고치는 속도 · 정확도 | △ Plugin API 자바스크립트를 작은 단계로 실행(write-to-canvas, **베타**). 결과 확인도 스크린샷 | ○ 텍스트 편집 | **◎ 텍스트 편집 + 자동 테스트(타입 · 화면 캡처 비교)** |
| 비용 (이 프로젝트는 무료만) | ✕ 드래프트 밖에 쓰려면 Full seat(유료), write-to-canvas 는 베타 뒤 사용량 기반 유료 예정, Code Connect 는 Organization 이상 | ○ 무료 | ○ 무료 |
| 사용자가 직접 끌어서 고치기 | **◎** | ○ 캔버스 편집기(단, 고치면 생성기 원본과 어긋남) | ✕ 말로 피드백 → Claude 가 수정(지금과 같은 방식) |
| 작은 단위로 쪼개기 | ○ | △ 파일 하나 = 컴포넌트 하나, props 제약 | ◎ 원자 → 분자 → 조직 → 페이지 |
| 상태(Tweaks) 보기 | 변형(variant) | Tweaks | 갤러리의 컨트롤 · 상태별 이야기(story) |
| 다크 모드 · 반응형 확인 | 수동 | 수동 | 갤러리 토글 + 자동 캡처 |
| 위험 | 도구 정책 · 가격 변경, 베타 기능 | 버릴 작업(구현하면 캔버스는 은퇴) | 첫 컴포넌트를 만드는 초기 비용(어차피 개발에서 해야 할 일) |

참고: Figma MCP write-to-canvas 는 Plugin API 로 컴포넌트 · 변수 · 오토 레이아웃을 만들 수 있지만 베타이고, 드래프트 밖 쓰기에는 Full seat 가 필요하며 베타 뒤 사용량 기반 유료 예정(Figma 개발자 문서). Code Connect 는 Organization · Enterprise 요금제 기능(포럼 답변 — 공식 가격표 확인 필요). Dev Mode 는 무료 Starter 에 없음(Figma 가격 FAQ).

## 4. 판단 — C (코드가 원본)

1. **100% 동기화가 목표라면 C 만 구조적으로 가능하다.** A · B 는 아무리 잘해도 "옮기기"가 남는다.
2. **Claude 가 가장 빠르고 정확하다.** 코드는 바꾼 뒤 바로 타입 검사 · 화면 캡처 비교로 "다른 페이지가 깨졌는지"를 확인할 수 있다. 피그마는 확인 수단이 스크린샷뿐이다.
3. **무료 원칙과 맞는다.** 피그마 경로는 쓰기 · 연결 기능이 유료 쪽에 있다.
4. **어차피 할 일이다.** 확정 순서(12-confirm-order)상 1묶음 확정 다음 단계가 "tokens.css 와 공통 컴포넌트를 SvelteKit 으로"다. 그 결과물이 곧 갤러리가 된다.
5. 잃는 것 — 사용자가 직접 끌어서 고치는 일. 지금도 피드백을 말로 주고 Claude 가 고치는 방식이라 실제 작업 흐름은 같다. 필요하면 피그마는 **아이디어 스케치용**(원본 아님)으로 쓸 수 있다.

## 5. C 의 모습

```
packages/ui (또는 apps/web/src/lib/ui)
  tokens.css                      ← 지금 docs/design/system/tokens.css 를 옮김
  atoms/      Button · Chip · Icon · Tooltip · Badge · CatFace · Count
  molecules/  PlatChip(+툴팁) · CountLine · GameCard · ReviewItem · MakerCard · InfoList · KeyFacts
  organisms/  Header · MediaViewer · GamePanel · ReviewList · CatalogFilters
  pages/      실제 라우트가 이 조각들을 조립
갤러리(Storybook)                 ← 컴포넌트마다 상태별 이야기(처음/해 본 적 있음/다운로드 …, 라이트/다크, 게스트/회원)
                                     + 페이지 이야기(가짜 데이터로 PG01 · PG05 전체)
게시                              ← `npm run design:publish` 가 정적 빌드를 지금처럼 비공개 아티팩트로 올림
검사                              ← Playwright 가 이야기마다 라이트 · 다크 캡처 → 바뀐 곳을 PR 에 표시
```

- 이름 규칙: 갤러리 경로를 캔버스 코드와 맞춘다(`Pages/PG05 게임 상세`, `Molecules/GameCard`). 피드백은 지금처럼 "PG05 …", "GameCard 다운로드 상태 …"로.
- 갤러리 도구: **Storybook**(컨트롤 = Tweaks, 접근성 · 상호작용 검사 내장). 설치할 때 SvelteKit 3 · Svelte 5 지원을 확인하고, 안 맞으면 앱 안 `/design` 경로(개발 빌드에서만, 같은 런타임)로 대체한다 — 어느 쪽이든 원본은 코드.
- 실제 구현에서 컴포넌트를 더 쪼개는 것은 자유 — 갤러리는 실제 쪼갠 단위를 그대로 보여 준다(차이가 생길 수 없음).

## 6. 옮겨 가는 순서 (제안)

1. **지금 ~ 1묶음 확정**: 캔버스 계속. 다만 복제를 줄이는 정리만 — 카드 · 헤더 · 칩을 생성기 한 모듈로 모으고, 손으로 만든 PG01 · DS04 도 생성기로 옮겨 한 곳 수정 = 전 페이지 반영(반나절 안팎). `dc-import` 로 캔버스를 본격 컴포넌트화하지는 않는다(곧 은퇴할 곳에 들일 비용).
2. **1묶음 확정 직후**: 토큰 → 원자 → 분자 순으로 코드 컴포넌트 + 갤러리 + 캡처 검사 세팅. 1묶음 페이지를 코드로 조립.
3. **구현된 페이지는 캔버스에서 은퇴**(보관 폴더로, 캔버스 페이지 메뉴에 "→ 갤러리" 표시). 아직 구현 안 된 묶음만 캔버스에서 기획 시안으로 다룬다.
4. 이후 모든 디자인 수정 = 코드 수정. 갤러리 아티팩트 자동 갱신.

## 7. 사용자가 정할 것

- C(코드 원본 + 갤러리)로 갈지, 그래도 피그마를 원본으로 할지(유료 · 동기화 한계 감수).
- 1단계(캔버스 생성기 정리)를 지금 할지, 바로 코드 컴포넌트로 넘어갈지.

## 8. 확정된 진행 방식 (사용자, 2026-11-27)

- 묶음 단위가 아니라 **페이지 하나씩**: Claude 가 페이지 우선순위를 설계하고, 한 페이지를 코드로 만들어 갤러리로 확인 → 확정되면 다음 페이지.
- **이미 만든 컴포넌트를 다른 페이지에서 쓰거나 조금 바꿔야 할 때는 사용자와 함께 검토한다.** Claude 가 먼저 ① 바꿔야 하는 이유 ② 영향받는 기존 페이지 · 컴포넌트 목록 ③ 전략 후보(기존 props 추가 · base 를 두고 확장 · 합성 컴포넌트 · 별도 컴포넌트 · 그대로 둠)와 장단점 · 추천을 내고, 결정 후 구현한다.
- 그 전에 **개발 환경 결정(컨벤션 · 린트 · 개발 방식 · 버저닝 · 아키텍처 …)을 먼저 끝낸다** — `docs/dev/setup-agenda.md`.
- 6절 1단계(캔버스 생성기 정리)는 하지 않는다 — 바로 코드로 간다. 캔버스는 아직 코드로 옮기지 않은 페이지의 기획 시안으로만 남는다.
